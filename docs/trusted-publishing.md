# GitHub Actions trusted publishing

Register the repository, product, tag/environment identity and hosted-signing policy with the private SocketJack publisher before using this workflow. Enable `id-token: write` only in the publishing job; keep environment protections in place. The generic client requests a fresh GitHub identity for audience `https://socketjack.com/installer-publisher`, exchanges it for a short-lived package-scoped credential, and never stores it or prints it. No publisher password, publisher access token or durable signing key belongs in the workflow.

For the tag-triggered template, register workflow path `owner/repository/.github/workflows/publish-installer.yml` without an `@` suffix, allowed ref `refs/tags/v*`, environment `installer-publishing`, and the repository's actual numeric repository/owner IDs. One policy then accepts successive tags: `v2026.10.25.1` authorizes package version `2026.10.25.1`, and the next numeric tag authorizes its matching version. The verified workflow reference must equal that exact path plus `@` and the verified triggering ref. The tag wildcard never authorizes a different package version, branches, pull requests, or forks. Exact branch/tag refs and legacy full workflow references keep exact matching; an optional reusable workflow pin must include its exact full reference (prefer a commit SHA).

Use the [tag-triggered workflow template](../templates/github-actions/trusted-publish.yml.example) with the application's existing installer build steps and its verified installer CLI distribution. Pin Actions to reviewed commit SHAs in the consuming repository. The template assumes an already-installed CLI; build/install that tool through the repository's established tooling before its publish step. Configure the required release environment and repository identity on the private service. A GitHub OIDC token authenticates the workflow; it does not automatically authorize an unregistered repository or product.

```powershell
heirowInstaller.Cli publish ./artifacts/draft.hinst --publisher https://socketjack.com --github-oidc --wait-for-activation
```

The API equivalent is `PublisherClient.PublishFromGitHubActionsAsync(packagePath, productId, version, options, cancellationToken)`. Use a connection without browser/account credentials. The client hashes and uploads the same read-locked file in bounded chunks. It checks GET upload state before transfer, resumes from the exact acknowledged offset, and renews credentials for the same upload/product/version/digest. Failed OIDC transfers remain on the service for bounded resume rather than being deleted. An explicit known upload can be resumed with `--resume-upload <id>`; repeating the same version and input digest reuses its receipt. The same version with different input is a conflict.

Receipts distinguish submission from activation: `status` is `pending`, `activated`, or `rejected`. `uploadedPackageSha256` and `uploadedSize` identify the original input; `sha256` and `size` identify the final sealed installer and can differ. Submission alone never means the application is available. `--wait-for-activation` polls the same receipt until active, rejected, cancelled or its 15-minute wait deadline. A timeout leaves the submission pending; it does not cancel server review. Existing release signature pins remain authoritative for installed delivery.

## Protected input descriptor

Place the declarative descriptor under `Modules.SocketJackSecurityLoader` in the input manifest. `formatVersion` is 1. Each component declares `id`, exact payload `sourcePath`, `executionMode` (`remote` or `local`), `entryType`, `runtime` (`net10.0` or `net8.0`), and component/assembly identifier `dependencies`. Operations map `id` to `componentId`. Each remote operation also declares bounded JSON objects `argumentsSchema` and `resultSchema` (8 KiB each). The private service accepts a closed schema subset and enforces it before and after execution; references, regular expressions, and external schema loading are unsupported. `publicPayload` explicitly identifies ordinary payload paths. `bootstrapPath` plus `bootstrapSha256`, when present, identify the private bootstrap carried by the signed final installer. The SDK validates paths and metadata; it contains no encryption, private worker implementation, or decryption keys.

An unsigned protected input is accepted by the CLI only when this descriptor explicitly requests `hostedSigning: true`; the service must independently authorize the registered hosted signer for that product. This input is not an installable trusted release. The private service seals protected content and signs the final package; clients install only the validated signed result. Omitted/false hosted signing retains ordinary signature requirements. Do not upload application-private sources to this public repository.

Set `preparationOnly: true` for a small component-sealing package that is not the complete application installer. Publishing accepts this boolean flag and the private builder preserves it. The installer rejects preparation-only packages, even with a valid trusted signature, before writing files or creating an application receipt. A non-boolean value is invalid. Embed the resulting sealed assets in the complete native application package, remove the preparation-only flag from its final descriptor, and sign that complete package through the existing trusted outer publisher; do not install the small preparation package as the canonical application.

The C# and VB startup templates in `templates/bootstrap/SocketJackSecurityLoaderStartup.*` take the installed private bootstrap's asynchronous entrypoint as a delegate. Invoke and await them before enabling protected functionality. Initialization failures propagate; do not continue into protected features or add a plaintext DLL fallback. These templates carry no authentication or protected runtime implementation.

## Trusted outer installer delegation

A sealed installable descriptor declares `formatVersion: 1`, the protected publisher's `publisherKeySha256`, mandatory `componentVersion`, and `components` containing distinct `id`, `path` under `SecurityLoader/` ending in `.sjsl`, and `componentDigest`. The package payload inventory must contain every referenced encrypted file plus `SecurityLoader/bootstrap.json`, `SecurityLoader/bootstrap.sig` and `SecurityLoader/bootstrap.pub`, with their exact signed payload hashes. `componentDigest` identifies the signed component envelope; it is distinct from the package's encrypted-file hash. The common `componentVersion` explicitly binds all declared components and may differ from the ordinary native application's package version. If a component also supplies `version` or `publisherKeySha256`, it must agree with the common release and publisher.

When an existing trusted installer publisher signs the outer application package and a hosted publisher signs the protected components, include `outerPublisherPin` with the existing outer publisher's SHA-256 fingerprint. The installer first verifies the actual outer signature against its external first-install trust pin or installed product's retained pin. Only that trusted signature can authorize a different child publisher through an explicit matching delegation. A supplied delegation must match even for same-key delivery; same-key delivery may omit it. A descriptor, bootstrap or embedded child public key cannot establish its own outer trust. This mechanism does not change installed publisher pins or grant CI/account permissions.

The trusted outer signature binds the complete descriptor, component identities/version/digests, delegated child fingerprint, bootstrap assets and encrypted payload inventory. Duplicate fields, identities, payload paths or component digests; absent release bindings; source drafts; mismatched delegation; untrusted outer signatures; and changed signed payload bytes are rejected. Installation, cached repair and updates continue to use the outer package's retained publisher pin. The private application runtime separately verifies the actual child bootstrap/component signatures and exact signed metadata and requests current online approval before unlocking code. The generic installer delivers sealed bytes and never decrypts or activates them.

## Completed native application delivery

Publish a small protected preparation draft with `preparationOnly: true` through hosted signing. Embed its exact approved ciphertext and signed bootstrap in the full native application payload, remove the preparation-only marker from that final descriptor, and sign the outer application using its existing registered publisher key. The installer refuses to install a preparation bundle as an application.

Native administrators select source quarantine explicitly with `PublishProtectedPreparationAsync(...)` or `--protected-preparation --token-env SESSION_BEARER`. Their ordinary installer publishing keeps its existing large-file lane. Approved non-administrator publishers continue using normal source publishing, and GitHub CI uses `--github-oidc`; neither uses the native administrator marker.

For the finished large package, use `PublisherClient.PublishSealedDeliveryAsync(packagePath, productId, version, cancellationToken)` or `heirowInstaller publish application.hinst --sealed-delivery --token-env SESSION_BEARER --trust-key EXISTING_OUTER_PIN`. Keep the native administrator session only in the calling process. This explicit lane binds the upload's account, product, version and package hash and rechecks authorization on subsequent requests. SocketJack verifies its registered outer signature, delegated hosted key and exact approved component assets before promotion. It retains the existing bounded large-file upload pipeline; protected source preparation retains its separate encrypted quarantine limit.

The final delivery lane requires a native administrator bearer session and rejects browser cookies and scoped CI credentials. GitHub trusted publishing continues to publish component preparation drafts without persistent account credentials; it does not grant administration or final-delivery privileges.

The explicit preparation and completed-delivery lanes accept full `.hinst` or standalone `.exe` inputs. Publish signed `.hupd` transitions through the ordinary file-update publisher; a file transition is not a component source draft or a full installer.
